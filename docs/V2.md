# V2.md — multi-tenant roadmap

v1 shipped as a single-user system, on purpose (CLAUDE.md: "single user, no
auth"). This document is the plan for making it a multi-user one. It is a
sibling of `ROADMAP.md`, not a replacement: phases here are numbered **V1–V5**
so they never collide with v1's Phases 0–6, and the same working agreement
applies — tests passing, ruff/mypy clean, status updated here, a DECISIONS
entry for every architectural choice.

Ordering principle: **isolate before you scale.** V1 and V2 change what the
system *is*; V3–V5 change how much of it there can be. Nothing in V3–V5 is
worth doing while any user can still read another user's repo.

The design rationale for all of it is in DECISIONS 2026-07-29 (six entries).
This file is the execution plan, not the argument.

**Hard requirement — already satisfied.** V2's migration is verified by running
`scripts/eval.py` before and after and demanding identical numbers, so the
baseline must be recorded and the corpus pinned *before* V1 begins. Both are
already true: EVAL.md carries the dated result blocks, the README table is
filled, and httpx sits in the database at the pinned `b5addb64` (825 impl / 697
test). Nothing in Phase 6's remaining work changes any of that.

*An earlier draft of this section claimed Phase 6 had to close first because the
baseline depended on it. That was wrong — it conflated "Phase 6 is formally
open" with "the thing V2 depends on is missing". Only the first is true.*

**Soft recommendation — ship `demo.gif` first anyway.** It is ~20 minutes, it is
the highest-leverage work left in v1, and starting a 2–3 week migration with v1
sitting 20 minutes from finished is how a project ends up with neither finished.
This is advice, not a gate.

**Two defects V2 would have inherited — both closed before V1 opened.** The
Phase 1 chunk spot-check found split class-skeleton chunks carrying synthetic
line numbers (69 of 1522 chunks; fixed in `3072252`), and the migration that
fixed it exposed a retrieval-wide missing tiebreaker that made tied results
depend on physical row order (fixed in `a6f6246`). Both mattered here
specifically: V2's whole verification is *"the numbers must not move"*, and
neither of those could be told apart from a migration error once V2 was
in flight. Deliberately cleared first.

**One piece of v1 paperwork is still open**, and is not a gate: `README.md`
still quotes pre-tiebreaker figures (fts hit@3 0.60, hybrid hit@5 0.85, fts MRR
0.503) and the naive column has not been re-measured since. **EVAL.md is
correct** and is what V2's before/after check reads, so the baseline is sound —
but fix the README before anyone cites it.

## Phase V1 — Identity & isolation

**Goal:** no request can reach a repo the caller does not own. Identity exists;
nothing else changes.

> **The hole this closes.** `_require_repo` (`routes.py:157`) checks a repo
> *exists*, never who owns it, and `GET /repos` (`routes.py:203`) returns every
> row in the table to every caller. Any caller who knows or guesses a repo UUID
> can list it, chat over it, and `read_file` its contents. This is the reason
> V1 is first and the reason nothing else is allowed to jump the queue.

Tasks:
- `006_users.sql`: `users` (id, github_id UNIQUE, login, name, avatar_url,
  created_at, last_seen_at) and `user_repos` (user_id, repo_id, added_at, PK on
  the pair). Purely additive — no existing table is rewritten. *(Numbered 006,
  not 005: the rendered-span fix took 005 first.)*
- Backfill the existing repo rows to a bootstrap user so nothing orphans — 12
  of 12 adopted
- `app/auth/`: GitHub OAuth callback, session issue + verify. **No password
  path, no signup form** (DECISIONS 2026-07-29). *Not* a JWT, as an earlier
  draft of this line said: there is no third party to verify it and no claim
  beyond a user id, so it is an opaque HMAC-signed string (SPEC §13.4)
- `api/deps.py`: a `CurrentUser` dependency alongside `Conn` / `Pool`
- `_require_repo` → `_require_owned_repo(conn, user_id, repo_id)`, raising the
  existing `RepoNotFoundError` for an unowned repo so the response is **404,
  not 403** — a 403 confirms the UUID exists
- `list_repos` joins `user_repos`; `create_repo` also writes the membership row
- `ratelimit.py`: identity becomes `user_id` on authenticated routes, IP on the
  rest. `TRUST_PROXY_HEADERS` stops being load-bearing for anything but logging
- Frontend: `useUser` hook, header sign-in/sign-out, and a `RequireAuth` gate
  on `/` and `/repos/*`. The session travels as an **HttpOnly cookie**, so what
  each fetch needs is `credentials: "include"` — in `lib/api.ts` *and*
  `lib/sse.ts` — rather than an `Authorization` header, though the backend
  accepts either (§13.4). Gating is client-side, not Next middleware: middleware
  only sees cookies on the frontend's own origin, which works on localhost by
  accident and breaks the first time the API gets its own domain
- `tests/api/test_tenancy.py`: the negative suite, as its own module

Done when:
- [x] As user A, every cross-tenant call against user B's repo returns 404:
      `GET /repos/{id}`, `POST /repos/{id}/chat`, `GET /repos/{id}/files` —
      proven by `tests/api/test_tenancy.py`, not by inspection. **24 tests.**
      Also pinned: an unowned repo and a nonexistent one are byte-identical
      apart from the id the caller supplied, so the pair is no existence
      oracle; and ownership is checked *before* readiness, so a stranger's
      indexing repo answers 404 rather than leaking its state through a 409.
- [x] `GET /repos` as user A never contains a repo owned only by user B
- [ ] Sign in with GitHub works end-to-end in the browser; the session survives
      a page refresh; the **chat SSE stream carries the auth header** (it is a
      `fetch` stream, not `EventSource`, so this needs no transport change)
      — **the one box left. Blocked on a registered OAuth app**: set
      `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `SESSION_SECRET` and
      `BOOTSTRAP_GITHUB_ID` in `backend/.env`. Code is complete on both sides;
      `credentials: "include"` is on every call including the SSE stream.
- [x] Rate limits key on `user_id` for authenticated routes and on IP for the
      rest, verified by test — including that two users behind one IP get
      separate buckets, and that a **forged** token falls back to the IP rather
      than minting a fresh quota (the token is verified, not merely parsed)
- [x] The benchmark corpus is intact and reachable by the bootstrap user:
      `SELECT count(*) FILTER (WHERE NOT is_test), count(*) FILTER (WHERE is_test) FROM chunks`
      still returns `825 | 697` for httpx — verified after `006` on the live
      database: **12 of 12 repos adopted, 0 orphans**
- [x] `ruff check`, `mypy app`, `pytest` clean; `tsc --noEmit` clean —
      **286 backend tests**; frontend `pnpm build`, `pnpm lint` and 30 vitest
      tests clean

Do not: add a password login or a signup form; put ownership checks inside the
six agent tools (DECISIONS 2026-07-29 — one check, one place); start the
snapshot split; touch retrieval.

## Phase V2 — Corpus snapshots

**Goal:** a repo at a commit becomes a shared, immutable artifact. Users hold
references to it, not copies of it.

> **The bug this closes.** `pipeline.py:238-239` calls `clear_repo_graph()` and
> `clear_repo_content()` at the *start* of every ingest, and `repos.url` is
> globally UNIQUE. One user re-ingesting `encode/httpx` deletes the corpus
> another user is mid-chat on, silently. Today that needs two users to collide;
> after V1 there will be thousands.

Tasks:
- `007_snapshots.sql`, data-preserving *(numbered 007 — 006 is `users`)*:
  - `repo_sources` (id, url UNIQUE, name)
  - `repo_snapshots` (id, source_id, commit_sha, strategy, status, error,
    progress columns), **`UNIQUE (source_id, commit_sha, strategy)`** — the
    two-column version this plan originally specified is wrong and the live
    data disproves it: httpx's AST and naive corpora sit at the *same* commit
    `b5addb64` and are separated today only by the `#naive` fragment this
    phase retires (SPEC §14.2, DECISIONS 2026-07-29)
  - `snapshot_id` added to `files` / `chunks` / `symbols` / `edges`, backfilled
    from `repo_id`
  - `user_repos.repo_id` → `snapshot_id`
- **Give each backfilled `repo_snapshots.id` the same UUID as its `repos.id`.**
  The V1 membership rewrite then becomes a rename rather than a remap
- **No re-embedding.** The migration is SQL row rewriting; every vector keeps
  its value. Re-embedding is the expensive part and is not needed
- `pipeline.py`: `clear_repo_*` leaves the normal path. A snapshot is written
  once and frozen; a retry discards the failed snapshot and starts a new one
- Dedup ordering: shallow-clone → read HEAD → **look for a ready snapshot at
  that SHA** → if found, short-circuit and link the user. This lookup is where
  the ingest-volume collapse actually happens
- Retire the `#naive` URL-fragment hack (`pipeline.py:73-78`). It exists only
  because `repos.url` is UNIQUE; a baseline corpus becomes a snapshot with
  `strategy='naive'`
- Keep the old `repo_id` columns for one release so the migration is reversible

Done when:
- [x] **`scripts/eval.py` reproduces the frozen Phase 6 baseline question for
      question.** Retrieval is a pure function of the corpus; if hit@k moved,
      the migration corrupted data. This is the criterion the phase lives or
      dies on — **all twelve metrics identical** through the new snapshot code
      path: vector 0.75/0.85/0.90 MRR 0.722, fts 0.55/0.70/0.80 MRR 0.463,
      hybrid 0.80/0.90/0.95 MRR 0.753
- [x] httpx still reports `825 | 697`, and a spot-checked chunk's embedding is
      byte-identical to its pre-migration value (proves nothing re-embedded) —
      **stronger than spot-checked**: sha256 over *all 1522* httpx embeddings is
      `17fb8fc8…7551` before and after `007`, and 0 rows across all five tables
      have `snapshot_id` differing from `repo_id`
- [x] Two users submitting the same repo at the same commit produce **one**
      ingest job and **two** library rows — `tests/api/test_snapshots.py`
- [x] A chat streaming against snapshot S is unaffected by another user
      ingesting the same source at a new commit — verified by an integration
      test that interleaves them, not by argument:
      `test_a_ready_snapshot_survives_another_ingest_of_the_same_source`
      captures the exact chunk ids S serves, runs a full second ingest at a
      *different commit*, and requires the identical id sequence afterwards
- [x] `#naive` appears nowhere in code or data; the naive corpus is reachable
      as `strategy='naive'` and `eval.py` still measures it — 0 sources with a
      `#naive` URL, 0 names with an `@naive` suffix, and both httpx corpora now
      sit under one source at commit `b5addb64` (ast 1522 chunks / naive 657)
- [ ] Rollback rehearsed once on a copy: `repo_id` columns still populated and
      the pre-migration queries still answer — **the one box left.** The columns
      are retained and populated for every migrated row, but new rows written
      after `008` carry NULL there, so a revert restores the pre-V2 corpus and
      loses anything ingested since. Rehearse before relying on it.

Do not: re-embed anything; drop the `repo_id` columns in this phase; change the
chunker, the header format, or the retrieval algorithm — any of those would
make the eval-equality check meaningless, which is the whole verification.

## Phase V3 — Ingest fleet & inference service

**Goal:** ingest throughput scales with machines, and the API stops carrying
torch.

Tasks:
- **Leases.** `claimed_by` / `claimed_at` on `repo_snapshots`, with a heartbeat.
  `sweep_zombie_repos` sweeps only *expired leases*, never "everything in
  flight at my startup" — see the note below
- Replace the global `count_active_ingests` with a **per-user** quota; one
  user's queue must not block another's
- Job dedup via a **DB unique constraint** on in-flight snapshots per
  `(source_id, commit_sha)`, not a Redis lock — the database is already the
  source of truth and cannot drift from it
- `max_jobs = 1` per worker stays; scale by process count
- `embedder.py` gains an `HttpEmbedder` implementing the existing `Embedder`
  Protocol; config selects the implementation. **Rule 3 is preserved** — still
  exactly one module that knows sentence-transformers exists
- The inference service itself: FastAPI, `/embed` + `/rerank`, request batching.
  Query embedding (one short string, latency-bound) and ingest embedding
  (thousands of chunks, throughput-bound) may be separate deployments of it

> **A bug this phase introduces, and must therefore fix.** `worker.py:117-119`
> justifies the startup sweep with "Startup is the moment we know for certain no
> such job is running." That is true for one worker and **false for N**. Worker
> 2 starting up will sweep worker 1's live job. The lease model is not a
> refinement; it is the precondition for a second worker existing.

Done when:
- [ ] Three workers ingest three distinct repos concurrently, and **no worker
      sweeps another's live job** — verified by starting a worker mid-ingest on
      another, not by reading the code
- [ ] Killing one worker mid-ingest leaves the other two unaffected; the orphan
      is swept only after its lease expires, then retried cleanly
- [ ] A per-user ingest quota refuses one user's 4th concurrent submission while
      a different user's submission proceeds in the same window
- [ ] API replicas run with **no torch import** — proven by an import check in
      the test suite, and by resident memory on a running replica
- [ ] `scripts/eval.py` numbers unchanged with the HTTP embedder in place
      (same corpus, same vectors, different transport)
- [ ] `ruff check`, `mypy app`, `pytest` clean

Do not: raise `max_jobs` above 1; move rerank into the API; skip the lease work
and "just be careful" about the sweep.

- **No-go:** it hasn't. Stay on V3's shape and revisit. At 100K chunks the work

## Phase V4 — Index & storage at scale

**Goal:** filtered vector search stays fast, and the primary database stops
holding every file of every repo.

> Extrapolated from the live instance (2,737 chunks → 21 MB `chunks`, 5.5 MB
> HNSW): ~15M chunks ≈ **115 GB** of table and **~30 GB** of HNSW index, which
> must be effectively resident to perform. That is the shape of the problem,
> measured small and scaled on paper — not a benchmark.

Tasks, cheapest first, each independently verifiable:
- `hnsw.iterative_scan = relaxed_order`. The instance runs **pgvector 0.8.1**,
  where this exists and is built for exactly this post-filter case. One setting;
  A/B it with `eval.py`
- Hash-partition `chunks` on `snapshot_id`, 64–256 partitions. Pruning routes a
  snapshot to one partition, each carrying a much smaller HNSW. Requires an
  index rebuild
- PgBouncer, transaction mode, with `statement_cache_size=0` for asyncpg. The
  existing `SET LOCAL hnsw.ef_search` is already transaction-pooling-safe
- File blobs → object storage. `routes.py:214-230` is already commit-keyed and
  immutable, so it maps onto a CDN with no logic change

Done when:
- [ ] The checkpoint trigger is **recorded with the measured number** that fired
      it, before any of this is built
- [ ] `hnsw.iterative_scan` A/B recorded as a dated block in EVAL.md, both
      settings, all modes
- [ ] Post-partition `eval.py` numbers unchanged, and p95 search latency
      improved against the recorded pre-partition figure
- [ ] Integration suite green through PgBouncer with `statement_cache_size=0`
- [ ] Files served from object storage with ETag/304 behaviour unchanged —
      the existing cache tests pass untouched

Do not: add a dedicated vector DB (DECISIONS 2026-07-24, reaffirmed
2026-07-29); do any of this before the checkpoint fires; partition on anything
but the column the queries actually filter on.

## Phase V5 — Cost, quota & fairness

**Goal:** every answer has a known cost, attributed to a user, and one user
cannot starve another.

Tasks:
- Token + cost accounting per agent run, written with the run, attributed to a
  user
- Per-user budgets, refused through a typed exception in `app/exceptions.py`
  mapped to 429 by the api layer — the existing `ServiceBusyError` pattern
- **Answer cache on `(snapshot_id, question_hash)`.** Only correct because V2
  made snapshots immutable; on shared popular repos the hit rate should be high
- Per-user chat concurrency checked **before** the global `chat_slots` gate, so
  fairness is enforced ahead of capacity
- `user_id` on every log line — `logging_setup.py` / `middleware.py` already
  plumb `request_id` through a `ContextVar`, so this follows an existing seam

Done when:
- [ ] Every agent run records tokens and estimated cost against a user; the
      numbers are queryable per user per day
- [ ] An over-budget user is refused with 429 and a `Retry-After`, in the same
      `{detail, request_id}` envelope as every other error
- [ ] A cache hit returns **identical citations** to the uncached run for the
      same question and snapshot
- [ ] One user cannot occupy more than their per-user slot allowance while
      another user's request is refused — verified by test
- [ ] `user_id` present on every log line and on the metrics that can carry it
      without minting a series per user

Do not: cache across snapshots; label Prometheus series by `user_id` (that
mints a series per user — the 2026-07-28 entry already records why raw-path
labelling was rejected for the same reason).

## v3 backlog (explicitly deferred)

- Organisations / teams / shared libraries — V1 ships **per-user** ownership
  only; a `user_repos` row is one user, and orgs are a second membership model
- Private repos via the stored GitHub OAuth token. The token is the point of
  choosing GitHub OAuth, but scope, refresh, and revocation are their own phase
- Snapshot retention / GC — nothing in V2 deletes an old snapshot; unreferenced
  ones accumulate until a policy exists
- Incremental re-index on new commits (inherited from the v1 backlog, and much
  more valuable once snapshots exist)
- Billing, plans, and anything that turns a quota into an invoice
- Everything still open in ROADMAP's v2 backlog: TypeScript grammar,
  commit-history indexing, symbol-graph mini-map, embedding-model upgrade pass,
  code-specific reranker

## Known risks

- **V2 is the risky phase.** It touches `queries.py`, `hybrid.py`, `tools.py`,
  and `pipeline.py` at once. The eval-equality check is the only thing standing
  between a subtle data error and a silently degraded product — treat a moved
  number as a blocker, never as noise.
- **The lease model in V3 is a correctness change disguised as a scaling
  change.** Getting it wrong means workers deleting each other's live jobs, and
  the symptom (a repo stuck mid-ingest) looks exactly like the bug the sweep was
  written to fix.
- **Auth scope creep.** GitHub OAuth is one provider and no password path. Every
  addition — a second provider, magic links, orgs — is a phase, not a task.
- **V4 built early is wasted work**, and worse, it is *invisible* waste: a
  partitioned index on a small corpus looks fine and buys nothing. The
  checkpoint exists to stop that.
- **Estimates.** V1–V5 total roughly 2–3 weeks of focused work. v1's phases ran
  long more often than short; plan accordingly.
